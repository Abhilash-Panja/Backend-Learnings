# Stage 3 — Spring Security Architecture 

> This version merges both drafts of Stage 3, reorders a few explanations for a smoother learning curve, and adds quick-reference tables/cheat sheets at key points so you can revisit concepts fast without re-reading everything.

We now know **why authentication exists** (Stage 1) and **why passwords need secure hashing** (Stage 2).

Now we open the Spring Security black box.

The goal of this stage is **not** to memorize:

```java
SecurityFilterChain
AuthenticationManager
AuthenticationProvider
UserDetailsService
SecurityContextHolder
```

The goal is to understand **why each one exists**, so that when the framework's API changes (and it will), you can reason your way through it instead of re-memorizing syntax.

---

## 🧭 Cheat Sheet — Read This First, Come Back to It Often

| Component | One-line job | Analogy |
|---|---|---|
| `SecurityFilterChain` | The ordered pipeline every HTTP request passes through before reaching your controller | Airport security checkpoint lanes |
| `Authentication` | An object representing "who is this / are they verified" | A boarding pass (claimed identity + verification status) |
| `AuthenticationManager` | Coordinates the authentication process; delegates the real work | The airport security manager |
| `AuthenticationProvider` | Knows how to verify **one specific type** of credential (password, JWT, OAuth...) | A specific security scanner (metal detector vs. passport scanner) |
| `UserDetailsService` | Given a username, fetches the security-relevant user info from your DB | HR lookup desk |
| `UserDetails` | Spring Security's standard shape for "a user," independent of your domain model | The standardized ID-card format the airport understands |
| `PasswordEncoder` | Verifies a raw password against a stored hash | The fingerprint matcher |
| `SecurityContext` | Holds the `Authentication` for the current request | The "verified" stamp on your boarding pass for this trip |
| `SecurityContextHolder` | Global access point to read the current `SecurityContext` | The gate agent's scanner that reads your stamped pass |
| `GrantedAuthority` / Role | What the authenticated identity is allowed to do | Your boarding zone / lounge access level |

**The one-sentence version of this entire stage:**

> Spring Security wraps every request in a pipeline that first figures out **who** is asking (Authentication), stores that identity somewhere the rest of the app can read (SecurityContext), and then decides **what** they're allowed to do (Authorization) — all *before* your controller ever runs.

---

# 1. The Problem We're Actually Solving

Suppose QueryNest receives:

```http
POST /api/v1/questions
```

The backend needs to answer two completely different questions:

```text
1. Who is making this request?        ← Authentication
2. Is this user allowed to do this?    ← Authorization
```

Without a security framework, the request path looks like:

```text
HTTP Request
     ↓
QuestionController
     ↓
QuestionService
     ↓
QuestionRepository
     ↓
Database
```

There's no step anywhere in there that establishes **identity**. We need security to sit *before* the controller:

```text
Client
   ↓
HTTP Request
   ↓
Spring Security  ← Authentication + Authorization happen here
   ↓
QuestionController
   ↓
QuestionService
   ↓
QuestionRepository
   ↓
Database
```

This single idea — **security wraps the request, it doesn't live inside individual controllers** — is the foundation for everything else in this stage.

---

# 2. Why Not Just Authenticate Inside Each Controller?

A beginner might write:

```java
@PostMapping("/questions")
public Question createQuestion(@RequestBody QuestionRequest request,
                                HttpServletRequest httpRequest) {
    // check token
    // find user
    // verify user
    // check permission
    // create question
}
```

It technically works — until you have dozens of endpoints:

```text
POST /questions
POST /answers
PUT /questions/{id}
DELETE /questions/{id}
GET /users/me
POST /comments
...
```

Now every single one repeats the same authentication logic. This creates five concrete problems:

| Problem | Why it hurts |
|---|---|
| **Duplication** | Same security code copy-pasted everywhere |
| **Inconsistency** | One endpoint might check auth slightly differently than another |
| **Maintenance cost** | Changing how auth works means touching every controller |
| **Security risk** | It's easy to *forget* to protect one endpoint |
| **Poor separation of concerns** | Controllers should talk HTTP ↔ DTOs, not implement security infrastructure |

Authentication is what's called a **cross-cutting concern** — a responsibility that applies uniformly across many unrelated parts of the app. Cross-cutting concerns belong in a layer that wraps the application, not scattered inside it.

```text
                 Security
                    ↓
              ┌───────────┐
HTTP Request → │ Security  │ → Controller
              └───────────┘
```

# 3. Why Filters Are the Right Tool

If security must happen *before* the controller, where can we intercept the request?

Servlet applications already have a built-in mechanism for this: **filters**.

```text
HTTP Request
     ↓
Filter
     ↓
Filter
     ↓
Filter
     ↓
Controller
```

A filter can inspect the request, look at headers/cookies, establish or reject identity, and decide whether to let the request continue to the next filter (and eventually the controller). This makes filters the natural home for web security logic.

### Why not one giant filter?

Because security itself has multiple distinct responsibilities:

```text
Filter A → authentication
Filter B → authorization-related processing
Filter C → exception handling
Filter D → session/security-context handling
...
```

This follows a core engineering principle: **give each component one focused responsibility instead of building one giant do-everything component.**

### `SecurityFilterChain`

This ordered sequence of filters is called the **Security Filter Chain**:

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) {
    ...
}
```

Don't memorize the syntax yet — understand the *need* it satisfies:

```text
Your security requirements
          ↓
SecurityFilterChain
          ↓
Ordered security filters
          ↓
Applied to every HTTP request
```

### `HttpSecurity`

`HttpSecurity` is the **configuration builder** you use to describe your security requirements — which endpoints are public, which need authentication, how sessions/CSRF should behave, etc.

```text
HttpSecurity
     |
     | you configure it
     v
SecurityFilterChain   ← the resulting pipeline
```

> **Key distinction:** `HttpSecurity` is how you *describe* your rules. `SecurityFilterChain` is the *pipeline* that results from those rules.

# 4. Authentication — Establishing "Who"

## 4.1 The `Authentication` Object

Spring Security represents the concept of authentication using an object called, unsurprisingly, `Authentication`. Think of it as a container carrying identity information through the request.

```text
Authentication
├── Principal      (who)
├── Credentials    (proof, e.g. password — usually cleared after auth)
├── Authorities    (what they can do)
└── authenticated  (true / false)
```

**Before verification** — someone just *claims* to be a user:

```text
Authentication
------------------------
principal    = abhilash
credentials  = MySecret123
authenticated = false
```

This basically means: *"Someone claims to be Abhilash and gave these credentials — please verify them."*

**After successful verification:**

```text
Authentication
------------------------
principal     = Abhilash
authorities   = [ROLE_USER]
authenticated = true
```

That's the crucial shift: from *"I claim to be..."* to *"Spring Security has verified this is..."*

## 4.2 Who Actually Performs the Verification?

We don't want to cram all verification logic straight into the filter chain — that's poor separation of responsibility. Instead, Spring Security introduces a coordinator:

### `AuthenticationManager`

> The component responsible for **coordinating** authentication. It doesn't necessarily do the verification itself — it delegates.

```text
Authentication Request
          ↓
AuthenticationManager
          ↓
Authentication (result)
          ↓
Success / Failure
```

### Why delegate? — `AuthenticationProvider`

QueryNest might eventually support multiple authentication mechanisms:

```text
Username/password
JWT
OAuth2
LDAP
...
```

We don't want one giant class handling all of them. So the `AuthenticationManager` hands the work off to the right specialist:

```text
                 AuthenticationManager
                         |
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      Provider A     Provider B     Provider C
   (password)         (JWT)         (OAuth2)
```

> **`AuthenticationProvider`**: knows how to verify *one specific type* of authentication request. For username/password, a common built-in is `DaoAuthenticationProvider`.

# 5. The Username/Password Flow, Step by Step

```text
Login Request (username + password)
     ↓
Authentication (unverified)
     ↓
AuthenticationManager
     ↓
AuthenticationProvider
     ↓
UserDetailsService   ─────→ "find this user"
     ↓
UserRepository → Database
     ↓
UserDetails (found)
     ↓
PasswordEncoder      ─────→ "does the password match the hash?"
     ↓
MATCH? → SUCCESS / FAIL
```

## 5.1 `UserDetailsService` — Why Not Just Use `UserRepository` Directly?

Good instinct to ask this. Here's the distinction:

| | Knows about |
|---|---|
| `UserRepository` | How to fetch QueryNest's `User` **domain entity** |
| `UserDetailsService` | How to give Spring Security a **standardized security-facing** representation of a user |

These are different responsibilities wearing similar clothes. `UserDetailsService` is an **adapter** between your domain model and Spring Security's authentication model:

```text
Spring Security
       ↓
"Find user: abhilash"
       ↓
UserDetailsService (your custom implementation)
       ↓
UserRepository
       ↓
User entity (domain)
       ↓
UserDetails (security-facing)
       ↓
back to Spring Security
```

QueryNest's `CustomUserDetailsService` exists precisely because Spring Security needs *a standardized way* to obtain your application's users — it doesn't want to assume your domain class is literally called `User` with exactly the fields it expects.

## 5.2 `UserDetails` vs your domain `User`

```text
Your domain User                  Spring Security's UserDetails
├── id                            ├── username
├── username                      ├── password
├── email                         ├── authorities
├── password                      └── account status flags
└── relationships to Q&A
     (questions, answers)
```

> `UserDetails` doesn't mean "this is your database entity." It means **"this is the minimum information Spring Security needs to reason about this user."**

## 5.3 `PasswordEncoder`'s Role in This Chain

Once the provider has the stored password hash (via `UserDetails`) and the raw login password, it hands both to the `PasswordEncoder`:

```text
Raw login password
       +
Stored password hash
       ↓
PasswordEncoder.matches(...)
       ↓
MATCH / FAIL
```

This is exactly the `PasswordEncoder` you learned about in Stage 2 — now you can see precisely *where* it plugs into the bigger picture.

# 6. After Authentication Succeeds — Where Does the Identity Live?

Authentication succeeded. Great — but the *next* request-processing step (your controller) still needs to know **who this is**. We need somewhere to park that identity for the duration of the request.

### `SecurityContext`

```text
SecurityContext
       |
       v
Authentication
       |
       v
Current authenticated user
```

Example:

```text
SecurityContext
└── Authentication
     ├── Principal    = Abhilash
     ├── Authorities  = [ROLE_USER]
     └── authenticated = true
```

### `SecurityContextHolder`

This is simply the **global access point** other parts of the app use to read the current `SecurityContext`:

```text
SecurityContextHolder
        |
        v
SecurityContext
        |
        v
Authentication
        |
        v
Current User
```

Anywhere in your code, you can ask "who is currently authenticated?" via `SecurityContextHolder` — without needing the request object passed around everywhere.

## 6.1 Why This Beats Passing `userId` in the Request Body

Imagine instead every endpoint required the client to send its own identity:

```json
{ "userId": 123, "question": "..." }
```

Nothing stops a malicious client from sending:

```json
{ "userId": 999, "question": "..." }
```

The server should **never** trust an identity claim coming from the request body. Instead:

```text
JWT / login credentials
       ↓
Verified by the server
       ↓
Authenticated identity
       ↓
SecurityContext
       ↓
Read by the application
```

The server decides who you are — not the request payload. This becomes critical once you implement ownership checks (Stage 9+): you compare the *authenticated* identity against the resource owner, never a client-supplied ID.

# 7. Principal, Authentication, and Authorities — Untangled

These three terms get confused constantly. Here's the clean breakdown:

```text
Authentication
├── Principal        →  WHO (the identity itself, e.g. a UserPrincipal/Abhilash)
├── Credentials       →  proof used during verification (usually cleared after success)
├── Authorities        →  WHAT they can do (e.g. ROLE_USER)
└── authenticated      →  verification status (true/false)
```

- **Principal = identity.** "Abhilash" himself.
- **Authentication = the whole envelope** — identity + proof + permissions + verification status.
- **Authorities = permissions/roles** attached to that identity, e.g. `ROLE_USER`, `ROLE_ADMIN`.

```text
Authentication
├── Principal = Abhilash
└── Authorities = [ROLE_USER]
```

### Role vs. Authority (conceptually)

| | Represents | Example |
|---|---|---|
| **Authority** | A specific, granular capability | `QUESTION_DELETE` |
| **Role** | A broad category that usually *implies* a bundle of authorities | `ROLE_ADMIN` |

Spring Security's engine ultimately deals in **authorities** — a "role" is really just a naming convention (prefixed `ROLE_`) for a coarse-grained authority. We'll go deeper when we reach `@PreAuthorize` and `hasRole()`/`hasAuthority()`.

---

# 8. Authentication ≠ Authorization (Again — Now With the Framework's Vocabulary)

Being authenticated only answers "who." It says nothing about "what they can do."

```text
Authentication
       ↓
Identity established
       ↓
Authorization
       ↓
Permission decision (ALLOW / DENY)
```

You can absolutely be authenticated and still be forbidden from an action.

## 8.1 This Is Exactly What Explains 401 vs. 403

| Status | Meaning | Example |
|---|---|---|
| **401 Unauthorized** | No valid authenticated identity for this request | Missing JWT, invalid JWT, expired token |
| **403 Forbidden** | Identity is known and verified, but not permitted to do this | Abhilash (ROLE_USER) tries an admin-only operation |

```text
401 → Authentication problem   ("I don't know who you are")
403 → Authorization problem    ("I know who you are, but no.")
```

Spring Security has dedicated hooks for each case:

- **`AuthenticationEntryPoint`** — decides what happens when an *unauthenticated* client hits a protected endpoint → typically produces `401`.
- **`AccessDeniedHandler`** — decides what happens when an *authenticated but unauthorized* client is denied → typically produces `403`.

# 10. Where Does JWT Actually Fit?

A very common beginner misconception:

```text
❌ Spring Security = JWT
```

That's wrong. **JWT is just one mechanism for carrying an already-established identity between requests.** The rest of the architecture above (AuthenticationManager, SecurityContext, Authorization...) still exists regardless of whether you use JWT, sessions, or OAuth2.

```text
JWT
 ↓
Contains authentication information
 ↓
Gets turned into an Authentication object
 ↓
Placed into SecurityContext
```

## 10.1 What a JWT Filter Actually Does

For a request like:

```http
Authorization: Bearer <JWT>
```

a JWT filter's job is narrowly scoped:

```text
Read token
   ↓
Validate token (signature, expiry)
   ↓
Extract identity (username/user id)
   ↓
Create an Authentication object
   ↓
Put it into SecurityContext
```

It is **not** responsible for deciding whether the endpoint is public, whether the user has the right authority, etc. — that's still the job of the broader authorization configuration. Don't stuff every security responsibility into the JWT filter; it has exactly one job — establish identity from the token.

We'll dig into JWT filters properly in a later stage — for now, just note where the puzzle piece fits.

# 11. Spring Security's Responsibility Boundaries (Team Roster)

Think of the components as employees with distinct job descriptions:

| Component | "My job is..." |
|---|---|
| Security Filter Chain | "I inspect every incoming request and run security processing." |
| AuthenticationManager | "I coordinate authentication." |
| AuthenticationProvider | "I perform one specific type of authentication." |
| UserDetailsService | "I find a user's security-relevant information." |
| PasswordEncoder | "I verify passwords." |
| SecurityContext | "I hold the current request's authentication." |
| Authorization layer | "I decide if this authenticated user can do this." |

Each abstraction earns its existence by owning exactly one part of a genuinely complex problem. This is *why* mature frameworks look intimidating at first — they're modeling a real, multi-part problem space, not adding complexity for its own sake.

---

# 12. Spring vs. Spring Boot vs. Spring Security

| Layer | Provides |
|---|---|
| **Spring Framework** | IoC, Dependency Injection, Beans, MVC, AOP, transactions — the foundation |
| **Spring Boot** | Auto-configuration, starter dependencies, embedded server, easy setup — convenience layer |
| **Spring Security** | Authentication, authorization, filters, security context, security configuration |

```text
Spring          →  foundation
Spring Boot      →  convenience / app setup
Spring Security  →  security framework
```

They cooperate but are **not interchangeable**. When you add the Spring Security dependency, Spring Boot auto-configures sensible defaults for you — which is exactly why security can feel "magical" at first. It isn't magic; it's auto-configuration reacting to your dependencies, beans, and conditions. Providing your own `SecurityFilterChain` bean is how you take that magic back into your own hands.

# 13. Tracing a Full Request — Two Outcomes

## 13.1 Unauthenticated Request

```text
POST /questions
      ↓
Security Filter Chain
      ↓
Authentication required
      ↓
No valid authentication found
      ↓
401
      X  ← Controller never executes
```

## 13.2 Authenticated + Authorized Request

```text
POST /questions
      ↓
Security Filter Chain
      ↓
JWT validated
      ↓
Authentication created
      ↓
SecurityContext populated
      ↓
Authorization succeeds
      ↓
QuestionController
      ↓
QuestionService
      ↓
QuestionRepository
      ↓
Database
```

## 13.3 Authenticated but Forbidden

```text
DELETE /questions/101
      ↓
Security Filter Chain
      ↓
JWT validated
      ↓
Authentication created
      ↓
SecurityContext
      ↓
Authorization
      ↓
User lacks permission
      ↓
403
      X  ← Controller/business logic never runs
```

This third case is exactly what will matter once we implement ownership checks (e.g., "only the question's owner can delete it").

# 14. What Spring Security Is *Not*

It's just as valuable to know the boundaries:

- **Not your user database.** That's still MySQL + `UserRepository`.
- **Not your domain model.** `User` ≠ `UserDetails`.
- **Not your complete business-authorization engine.** Domain rules like "must own the question AND question must not be locked" still live in your service layer.
- **Not JWT itself.** JWT is one pluggable authentication mechanism among several possible ones.

---

# 15. Senior-Engineer Reasoning Pattern (For When the API Changes)

Frameworks evolve — class names get deprecated, APIs get renamed. When that happens, don't ask *"what annotation replaces this?"* first. Ask, in order:

```text
1. What problem was the old component solving?
2. What component now solves that problem?
3. Where does it participate in the request pipeline?
4. What information flows in and out of it?
```

That's how you stay productive even when Spring Security's surface API shifts under you — because you're reasoning from the *architecture*, not from memorized syntax.

---

# 16. Stage 3 Mental Model — The Paragraph You Should Be Able to Say From Memory

> "Spring Security intercepts HTTP requests through a security filter chain. Authentication is responsible for establishing the identity of the requester. An `AuthenticationManager` coordinates authentication and delegates to an appropriate `AuthenticationProvider`. For username/password authentication, the provider obtains user information through `UserDetailsService` and verifies the supplied password using `PasswordEncoder`. Once authentication succeeds, an `Authentication` object represents that identity and is stored in the `SecurityContext`. Authorization then uses the authenticated identity and its authorities to decide whether the request is allowed. If authentication fails, the request results in 401; if authentication succeeds but authorization fails, it results in 403."

If you can say that in your own words without looking, you understand this stage.
