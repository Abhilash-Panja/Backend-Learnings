# 5. The First Security Problem

Imagine QueryNest has this endpoint:

```http
POST /api/v1/questions
```

The user sends:

```json
{
  "title": "How does Spring Security work?",
  "description": "I want to understand authentication."
}
```

The backend receives the request.

The question is:

> Who is creating this question?

Without authentication, the backend has no reliable answer.

It knows:

```text
Title
Description
```

but it does not necessarily know:

```text
User identity
```

That is a fundamental security problem.

# 6. Why Does Identity Matter?

Suppose we have two users:

```text
User A
id = 101
username = abhilash

User B
id = 102
username = rahul
```

User A creates:

```text
Question #500
```

We need the database relationship to become:

```text
Question #500
       |
       v
User #101
```

Now suppose User B wants to modify Question #500.

The backend must answer:

> Is the current requester allowed to modify this question?

That requires knowing the requester's identity.

Without authentication:

```text
HTTP Request
     |
     v
QuestionController
     |
     v
QuestionService
     |
     v
"Who is this?"
     |
     v
?????????????
```

The application has no trustworthy answer.

# 8. Why `X-User-Id` Is Not Authentication

Suppose User A is:

```text
id = 101
```

The client sends:

```http
X-User-Id: 101
```

The server might say:

> Okay, this is User 101.

But what prevents User B from sending:

```http
X-User-Id: 101
```

?

Nothing, unless some other security mechanism verifies the identity.

That means a malicious client could potentially say:

```text
"I am user 101."
```

and the server has no cryptographic proof.

This gives us a fundamental security principle:

> **Never treat an identity supplied by the client as trustworthy merely because the value looks valid.**

# 9. Naive Authentication

Imagine we build authentication ourselves.

We might create something like:

```text
Client
  |
  | username + password
  v
Controller
  |
  v
UserService
  |
  v
Database
```

The controller could do:

```text
1. Receive username
2. Receive password
3. Find user
4. Compare password
5. Decide whether login succeeds
```

At first this seems easy.

But now ask:

> Where do we perform authentication for every future request?

We might create:

```text
if authenticated:
    continue
else:
    reject
```

inside every controller.

For example:

```text
QuestionController
    -> authentication check

AnswerController
    -> authentication check

UserController
    -> authentication check

VoteController
    -> authentication check
```

This is already becoming problematic.

---

# 10. Why Authentication Should Not Be Repeated Inside Controllers

Imagine we have 50 endpoints.

If authentication logic is inside controllers:

```text
Controller 1
    authentication

Controller 2
    authentication

Controller 3
    authentication

...

Controller 50
    authentication
```

Now we have:

* duplicated logic
* inconsistent behavior
* difficult maintenance
* higher chance of security bugs
* authentication mixed with business logic

More importantly, authentication is not really a business operation.

Creating a question is business logic.

Checking whether a request is authenticated is a cross-cutting security concern.

These should be separated.

---

# 11. Where Should Security Live?

Our architecture should become:

```text
Client
  |
  v
Security Layer
  |
  v
Controller
  |
  v
Service
  |
  v
Repository
  |
  v
Database
```

This is the key architectural idea behind Spring Security.

Security should happen **before the request reaches your business layer** whenever possible.

---

# 12. Why This Is Powerful

Without a security layer:

```text
Client
   |
   v
Controller
   |
   v
Service
```

With a security layer:

```text
Client
   |
   v
Security
   |
   v
Controller
   |
   v
Service
```

Now the controller can operate under an assumption:

> If this endpoint requires authentication, the security layer has already processed the request.

This creates separation of responsibility.

# 13. Authentication vs Authorization

Before we go further, we need to separate two concepts.

## Authentication

Authentication answers:

> **Who are you?**

Example:

```text
Username: abhilash
Password: ********
```

The system verifies the credentials.

Result:

```text
User = Abhilash
```

---

## Authorization

Authorization answers:

> **What are you allowed to do?**

Suppose:

```text
User A
    |
    +-- owns Question 101
```

User A may be allowed to:

```text
UPDATE Question 101
DELETE Question 101
```

But perhaps:

```text
User A
    |
    X
    |
Question 202
    |
User B
```

User A should not be allowed to delete Question 202.

So:

```text
Authentication
      |
      v
"Who is this?"
      |
      v
User A
      |
      v
Authorization
      |
      v
"What can User A do?"
```

# 24. What Spring Security Is Actually Solving

At a high level, Spring Security provides infrastructure for:

```text
1. Identifying the requester
2. Verifying credentials
3. Establishing authentication
4. Keeping authentication information available
5. Checking authorization
6. Rejecting unauthorized requests
7. Handling authentication/security errors
```

It does not replace your business logic.

It does not know what a Question fundamentally means.

It does not manage your QuestionService.

Instead:

```text
Spring Security
       |
       | security responsibility
       v
Your application
       |
       | business responsibility
       v
QueryNest domain
```

At the end of Stage 0, you should be able to explain:


# 34. The Most Important Engineering Insight

Don't think:

> "Spring Security is a collection of annotations."

Think:

> **"Spring Security is an infrastructure system that establishes and evaluates security information around an HTTP request."**

Then the annotations and classes make much more sense.

For example:

```text
Need:
"Only authenticated users can create questions."

          ↓

Security requirement

          ↓

Need:
"Determine whether request is authenticated."

          ↓

Authentication mechanism

          ↓

Need:
"Make authentication available to the application."

          ↓

SecurityContext

          ↓

Need:
"Reject unauthenticated requests."

          ↓

Security exception handling

          ↓

Need:
"Define which URLs require authentication."

          ↓

Authorization configuration
```

Now the syntax becomes the last step, not the first.

# Understanding Why QueryNest Needs Security Before Learning Spring Security

## My Initial Mistake

When I first started learning security, my thinking was:

> We use security because some APIs should be private.

That is true, but it is not the actual problem.

The deeper problem is:

```text
How does the server know
who is making a request?
```

Everything else comes from this question.

---

## QueryNest Without Security

QueryNest is a normal Spring Boot REST API.

The flow looks like:

```text
HTTP Client
     |
     v
Controller
     |
     v
Service
     |
     v
Repository
     |
     v
MySQL
```

The application supports:

```text
Users
Questions
Answers
Votes
```

At first glance this architecture looks complete.

But there is a missing piece.

---

## The First Problem

Suppose someone sends:

```http
PUT /api/v1/questions/101
```

with:

```json
{
  "title": "New Title"
}
```

The backend receives the request.

Now a very important question appears:

```text
Who is trying to update Question 101?
```

The request contains:

```text
Question ID
New title
```

But it does not automatically contain a trustworthy identity.

Without identity, the backend cannot decide whether the update should be allowed.

---

## Why Identity Matters

Suppose:

```text
User 101 owns Question 500
```

Now:

```text
User 101
```

tries to update it.

That should be allowed.

But if:

```text
User 102
```

tries to update it, that should be rejected.

To make that decision the server must know:

```text
Who is making the request?
```

Without that information:

```text
Ownership checks are impossible.
Authorization is impossible.
```

---

## Why X-User-Id Is Unsafe

Imagine the client sends:

```http
X-User-Id: 101
```

At first it looks useful.

But what prevents another user from sending:

```http
X-User-Id: 101
```

as well?

Nothing.

The server sees an ID.

But it does not have proof that the requester is actually User 101.

This taught me an important principle:

```text
Valid ID
≠
Verified Identity
```

A client claiming an identity is not the same as proving it.

---

## Authentication vs Authorization

I initially mixed these concepts together.

Now I think about them like this:

### Authentication

Authentication answers:

```text
Who are you?
```

Example:

```text
Current User = User 101
```

The system has verified the identity.

---

### Authorization

Authorization answers:

```text
What are you allowed to do?
```

Example:

```text
User 101 owns Answer 500
```

User 101 can delete it.

But:

```text
User 102
```

cannot delete it.

---

## QueryNest Example

Suppose:

```text
Answer 500
Owner = User 101
```

User 102 logs in successfully.

That means:

```text
Authentication = Success
```

But if User 102 tries:

```http
DELETE /api/v1/answers/500
```

then:

```text
Authorization = Failure
```

because the answer belongs to another user.

This was an important realization:

```text
Authentication can succeed
while authorization fails.
```

---

## Why Not Put Authentication Inside Every Controller?

Initially I thought we could simply check authentication inside controllers.

Something like:

```text
QuestionController
    authentication

AnswerController
    authentication

VoteController
    authentication
```

But this creates several problems:

```text
Code duplication
Maintenance difficulty
Inconsistent behavior
More security bugs
Mixing business logic and security logic
```

Controllers should focus on business operations.

For example:

```text
Create Question
Update Answer
Delete Vote
```

not on verifying every request.

---

## A Better Architecture

Instead of putting security logic inside controllers, we place it before the application logic.

```text
Client
  |
  v
Security Layer
  |
  v
Controller
  |
  v
Service
  |
  v
Repository
  |
  v
Database
```

Now invalid requests can be rejected early.

There is no reason to execute controllers, services, repositories, or database queries if the request should already be denied.

---

## Public vs Protected Endpoints

Another thing I learned is that not every endpoint needs protection.

Examples of public endpoints:

```text
Register User
Login
Read Questions
Search Questions
```

Examples of protected endpoints:

```text
Create Question
Update Question
Delete Question
Create Answer
Delete Answer
Vote
```

Security is not:

```text
Protect everything.
```

Security is:

```text
Define who can access what.
```

---

## The Stage 0 Mental Model

At the end of Stage 0, my understanding is:

```text
QueryNest needs a trustworthy identity
for each request.

Once identity is established:

1. We know who the user is.
2. We can enforce ownership rules.
3. We can decide what actions are allowed.

Instead of implementing these checks
inside every controller, security should
exist as a separate infrastructure layer
that processes requests before business
logic executes.
```
