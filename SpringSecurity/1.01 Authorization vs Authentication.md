# Stage 1 — Authentication vs Authorization

Let's build these two concepts from the ground up, using your actual QueryNest scenarios instead of definitions.

---

## 1. Start With the Real Question the Server Must Answer

Every incoming request to QueryNest eventually needs the server to answer two *separate* questions:

```text
Question A: Who is sending this request?
Question B: Is that sender allowed to do this specific thing?
```

These sound similar, but they are answered by completely different mechanisms, at completely different moments, using completely different data.

Let's derive why, using your actual endpoints.

---

## 2. Walking Through QueryNest's Real Operations

### a) `POST /api/v1/users` — Registration

```json
{ "username": "abhilash", "email": "abhilash@example.com", "password": "secret" }
```

At this point, there is no user yet. There's nothing to authenticate — you can't ask "who are you?" to someone who doesn't have an account. So this endpoint is neither an authentication check nor an authorization check. It's the *creation* of the thing that authentication will later verify.

### b) `POST /api/v1/auth/login`

```json
{ "username": "abhilash", "password": "secret" }
```

Here the user is claiming an identity ("I am abhilash") and proving it (by supplying the correct password). The server's job is purely:

```text
Is this claim backed by valid proof?
```

That's it. Nothing about *permissions* happens here. The server isn't yet asking "can abhilash delete question 500?" — it's only asking "is this really abhilash?"

This is **100% authentication**.

### c) `POST /api/v1/questions` — Create a question

Once abhilash has a JWT (proof of identity), he calls this endpoint. The server now needs to know:

```text
Who is creating this question? → abhilash (authentication, already established)
Is "being authenticated" enough to create a question? → yes, per your rule table
```

So this endpoint requires authentication, but authorization here is trivial — "any logged-in user can create a question." There's no ownership check needed *yet* because the resource doesn't exist until this call creates it.

### d) `PUT /api/v1/questions/101` — abhilash edits **his own** question

```text
Step 1 (Authentication): Who is this? → abhilash, user id 101
Step 2 (Authorization): Does abhilash own question 101? → yes → allowed
```

### e) `PUT /api/v1/questions/202` — abhilash tries to edit **rahul's** question

```text
Step 1 (Authentication): Who is this? → abhilash, user id 101 — SUCCEEDS
Step 2 (Authorization): Does abhilash own question 202? → no (owner = rahul, 102) → denied
```

Notice something critical: **authentication succeeded** in both (d) and (e). Abhilash proved who he is perfectly well. He is *not* an impostor. But in case (e), being a legitimate, verified user still isn't enough — the rule isn't "any logged-in user can edit any question," it's "the owner can edit their own question."

This is the cleanest possible illustration of why these are two separate concepts:

```text
Authentication asks: "Is this really abhilash?"
Authorization asks:  "Even granting that it's really abhilash, is he
                       allowed to do THIS THING to THIS RESOURCE?"
```

### f) `DELETE /api/v1/answers/900` — abhilash deletes rahul's answer

Same shape as (e). Authentication succeeds (it really is abhilash). Authorization fails (abhilash ≠ answer owner).

---

## 3. Why This Split Matters Architecturally

If you collapse these into one check, you get bugs like:

```text
"If the user has a valid JWT, let them do anything."
```

That's authentication doing authorization's job — and it's exactly how a user ends up deleting someone else's answer. Keeping them conceptually separate forces you to ask **two different questions at two different layers**, which is exactly why Spring Security models them as two distinct concerns (you'll see this concretely in Stage 3 with `AuthenticationManager` vs `AccessDeniedHandler`/authorization checks).

---

## 4. Now Let's Build the Vocabulary — Logically, Not by Memorizing

### Identity
The *claim* of who someone is. `username = abhilash` is an identity claim. A claim alone proves nothing — anyone can *type* "abhilash" into a username field.

### Credentials
The *proof* backing that claim. In QueryNest, this is the password. The reason authentication works is: only the real abhilash (presumably) knows the password that hashes to the value stored against his row in the `User` table. Credentials are what convert an unverified claim into a verified one.

### Principal
Once authentication succeeds, the system needs a name for "the verified identity we're now operating as." That's the **principal** — the *authenticated result*, not the raw input. In your repo this shows up as `UserPrincipal`. Notice the shift:

```text
Before login: raw username/password (unverified claim + proof)
After login:  a Principal (verified identity the rest of the system can trust)
```

This is a subtle but important idea: once you're authenticated, the application stops thinking in terms of "username + password" and starts thinking in terms of "this Principal." Everything downstream (SecurityContext, authorization checks, `@AuthenticationPrincipal` injections) works off the Principal, never the raw password again.

### Roles
A role is a coarse-grained label for "the kind of user this is" — e.g., `ROLE_USER`, `ROLE_ADMIN`. In your `Role.java`, this is presumably an enum tied to `User`.

### Authorities
"Authority" is Spring Security's more general term — a role is *one kind* of authority (`GrantedAuthority`), but authorities can also represent finer-grained permissions like `CAN_DELETE_ANY_ANSWER`. Roles are really just authorities with a naming convention (`ROLE_` prefix) and special handling in some APIs.

### Permissions
The actual, specific "is this allowed" decision for a specific action on a specific resource. This is the layer where **ownership** lives — "abhilash may edit question 101" is a permission decision, and notice it can't be answered by role/authority alone. `ROLE_USER` doesn't tell you which questions a user owns. That's why ownership authorization (Stage 9 later) needs a database lookup, not just a role check.

Putting it together as one chain, using scenario (e):

```text
Identity claim:  "I am abhilash" (JWT username claim)
        ↓
Principal:       UserPrincipal{id=101, username=abhilash, authorities=[ROLE_USER]}
        ↓
Role/Authority:  ROLE_USER  → confirms abhilash is *a* valid user (coarse-grained)
        ↓
Permission:      Does user 101 own question 202?  → NO → 403
```

Role/authority checks can only ever get you the coarse-grained answer ("this is a logged-in user," "this is an admin"). Ownership-style permission checks require actually consulting the data.

---

## Mental Model Summary

```text
Authentication  →  establishes WHO is making the request (once, per request lifecycle)
Authorization   →  decides WHAT that established identity may do (can happen at
                    multiple points: URL-level coarse checks, then resource-level
                    ownership checks)

Identity       = the claim
Credentials    = the proof
Principal      = the verified identity, used everywhere after login
Role/Authority = coarse-grained "what kind of user" label
Permission     = the fine-grained, often data-dependent "may this user do X to
                 resource Y" decision
```
