# Stage 1 — Authentication vs Authorization

We are now moving from **“Why does QueryNest need security?”** to the next question:

> **What exactly does “security” mean when a request enters QueryNest?**

The two foundational concepts are:

```text
Authentication
        ↓
Who are you?

Authorization
        ↓
What are you allowed to do?
```

I checked the current QueryNest repository again before this stage. Your domain model gives us a very good real-world example: `User` owns `Question` and `Answer`, while `Question` belongs to a `User` and `Answer` belongs to both a `Question` and a `User`. ([GitHub][1])

---

## 1. Start With a Real QueryNest Request

Forget Spring Security for a moment.

Imagine this request:

```http
PUT /api/v1/questions/101
```

The user wants to change Question `101`.

The request contains:

```json
{
  "title": "Updated Spring Security question",
  "description": "Updated description"
}
```

The backend needs to answer **two completely different questions**.

### Question 1

> Who is sending this request?

That is **authentication**.

### Question 2

> Is that person allowed to modify Question 101?

That is **authorization**.

This distinction is the foundation of everything we will build.

---

# 2. Authentication: “Who Are You?”

Let's use a simple analogy.

Imagine you enter an office building.

The security guard asks:

> “Who are you?”

You show your employee ID.

The guard verifies:

```text
Employee ID
      ↓
Company records
      ↓
Valid?
```

If valid:

```text
You = Abhilash
```

That is authentication.

In software:

```text
Credentials
     ↓
Verification
     ↓
Identity
```

For example:

```text
username = abhilash
password = ********
```

The server verifies the credentials.

If they are valid:

```text
Authenticated user = Abhilash
```

---

# 3. What Does Authentication Actually Produce?

This is an important engineering question.

Authentication is not merely:

```text
true / false
```

A successful authentication gives the application an **identity**.

Conceptually:

```text
Authentication
      ↓
"User 101 is making this request"
```

Later, other parts of the application can use that identity.

For example:

```text
Current user
     ↓
User ID = 101
Username = abhilash
Role = USER
```

This information becomes useful when authorization starts.

---

# 4. QueryNest Example

Your `User` entity contains:

```text
id
name
email
username
password
role
```

and relationships to questions and answers. ([GitHub][2])

Suppose:

```text
User
----------------
id       = 101
username = abhilash
role     = USER
```

After successful authentication, conceptually the application knows:

```text
Current Requester
       ↓
User 101
```

We haven't discussed **how** Spring Security stores this information yet.

That's coming later.

For now, understand the concept:

> Authentication establishes the identity associated with the request.

---

# 5. Authorization: “What Are You Allowed to Do?”

Now imagine the office again.

The security guard has established:

```text
You = Abhilash
```

But that doesn't mean you can enter every room.

For example:

```text
Employee
   |
   +-- Office ✓
   |
   +-- Meeting room ✓
   |
   X-- Server room
   |
   X-- CEO office
```

You are authenticated.

But you don't automatically have permission to do everything.

That's authorization.

---

# 6. QueryNest Example

Suppose:

```text
User 101 = Abhilash
User 102 = Rahul
```

And:

```text
Question 500
       |
       ↓
Owner = User 101
```

Now User 101 sends:

```http
PUT /api/v1/questions/500
```

We already know:

```text
Who?
↓
User 101
```

Now we ask:

```text
Can User 101 update Question 500?
```

Yes.

Because:

```text
Authenticated User = 101
Question Owner     = 101
```

Therefore:

```text
Authentication = SUCCESS
Authorization  = SUCCESS
```

---

# 7. Now Change One Thing

User 102 sends the same request:

```http
PUT /api/v1/questions/500
```

Authentication succeeds.

Why?

Because User 102 has valid credentials.

So:

```text
Authentication = SUCCESS
```

But:

```text
Question Owner = 101
Current User   = 102
```

Therefore:

```text
Authorization = FAILURE
```

The important lesson:

> **A user can be authenticated but not authorized.**

This is one of the most important concepts in backend security.

---

# 8. Three Different Situations

There are actually three useful cases.

## Case A — Nobody is authenticated

```text
Request
  ↓
Who are you?
  ↓
No identity
```

Result:

```text
Authentication = FAILURE
```

Typically:

```http
401 Unauthorized
```

---

## Case B — User is authenticated and allowed

```text
Request
  ↓
User 101
  ↓
Allowed to perform operation
```

Result:

```text
Authentication = SUCCESS
Authorization  = SUCCESS
```

Typically:

```http
200 OK
```

or:

```http
201 Created
204 No Content
```

depending on the operation.

---

## Case C — User is authenticated but not allowed

```text
Request
  ↓
User 102
  ↓
Not allowed to modify resource owned by User 101
```

Result:

```text
Authentication = SUCCESS
Authorization  = FAILURE
```

Typically:

```http
403 Forbidden
```

This distinction will later explain most of the difference between **401 and 403**.

---

# 9. The Most Important Diagram So Far

Memorize the **logic**, not the words:

```text
                  HTTP REQUEST
                       |
                       v
              ┌─────────────────┐
              │ Authentication  │
              └────────┬────────┘
                       |
             "Who is this?"
                       |
              ┌────────┴────────┐
              |                 |
            FAIL              SUCCESS
              |                 |
              v                 v
            401          Authenticated User
                                |
                                v
                       ┌─────────────────┐
                       │ Authorization   │
                       └────────┬────────┘
                                |
                       "Can they do it?"
                                |
                       ┌────────┴────────┐
                       |                 |
                     FAIL              SUCCESS
                       |                 |
                       v                 v
                     403          Controller/Business
                                     Logic
```

This is much more important than knowing any Spring Security annotation.

# 10. Why Can't Authentication and Authorization Be the Same Thing?

Because identity and permission are different dimensions.

Consider:

```text
User = Abhilash
```

That's identity.

Now consider:

```text
Can Abhilash delete Question 500?
```

That's permission.

One user can have:

```text
Authentication:
    Abhilash

Authorization:
    Can read questions
    Can create questions
    Can update own questions
    Cannot update other users' questions
```

So:

```text
Identity ≠ Permission
```

Your data model says:

```text
User
 ├── Questions
 └── Answers
```

and:

```text
Question
 ├── User
 └── Answers
```

while:

```text
Answer
 ├── User
 └── Question
```

This means ownership is naturally represented in the domain. ([GitHub][1])

Suppose:

```text

   |
   +---- Question 1
   +---- Question 2
   +---- Answer 10
   +---- Answer 20
```

and:

```text
User 102
   |
   +---- Question 3
   +---- Answer 30
```

Now the authorization problem becomes very clear.

# 12. Authentication Establishes This

After login:

```text
Current User = 101
```

That's all authentication needs to establish.

It doesn't necessarily decide whether User 101 can modify a particular resource.

---

# 13. Authorization Uses That Identity

Now the application receives:

```text
PUT /questions/3
```

It finds:

```text
Question 3
      |
      ↓
Owner = User 102
```

Then compares:

```text
Current User = 101

Question Owner = 102
```

Result:

```text
101 != 102
```

Therefore:

```text
DENY
```

This is resource-level authorization.

---

# 14. Important: Authorization Isn't Always About Ownership

Ownership is only one type of authorization.

There are several common levels.

### Level 1 — Public

Anyone can access.

Example:

```text
GET /questions
```

---

### Level 2 — Authenticated users

Anyone with a valid identity can access.

Example:

```text
POST /questions
```

---

### Level 3 — Role-based

Only users with a particular role can access.

For example:

```text
ADMIN
```

might be allowed to delete any user.

---

### Level 4 — Resource ownership

Only the owner can modify the resource.

Example:

```text
User 101 → Question 101
```

Only User 101 can update it.

---

### Level 5 — Fine-grained business authorization

The rule can be more complicated.

For example:

```text
User must own the question
AND
question must not be locked
AND
user must have editing permission
```

This is where authorization becomes business logic rather than simply URL configuration.

---

# 15. Roles vs Permissions

Now we need another distinction.

Suppose QueryNest has:

```text
USER
ADMIN
```

A role is a broad classification.

For example:

```text
USER
```

might mean:

```text
Normal application user
```

while:

```text
ADMIN
```

might mean:

```text
Application administrator
```

But saying:

```text
User = ADMIN
```

doesn't necessarily describe every possible permission.

---

# 16. Role as a Group of Capabilities

Think of a role as a label that can represent a set of permissions.

For example:

```text
USER
 |
 +-- create question
 +-- create answer
 +-- vote
 +-- update own question
 +-- update own answer
```

while:

```text
ADMIN
 |
 +-- all normal operations
 +-- delete users
 +-- moderate questions
 +-- moderate answers
```

The role helps establish broad access.

But ownership still matters.

An admin might have broad privileges, while a normal user may need an ownership check.

---

# 17. Role vs Authority

Spring Security introduces terminology such as:

```text
Role
Authority
GrantedAuthority
```

Don't memorize these yet.

The conceptual distinction is:

```text
Role
   ↓
Broad category

Authority
   ↓
Specific capability/access decision input
```

For example:

```text
ROLE_ADMIN
```

could represent:

```text
Administrator
```

while an authority could conceptually represent:

```text
QUESTION_DELETE
```

We will later see exactly how Spring Security represents these.

---

# 18. Why This Matters

Suppose we write:

```text
Only ADMIN can delete questions.
```

That's a role-based rule.

But what if the requirement is:

```text
A USER can delete their own question,
but not somebody else's.
```

A role alone cannot solve that.

Both users may have:

```text
ROLE_USER
```

So:

```text
Role(User A) = USER
Role(User B) = USER
```

Yet:

```text
User A can delete Question 101
User B cannot delete Question 101
```

Why?

Because the authorization decision depends on **resource ownership**, not merely role.

This is a critical backend engineering distinction.

# 20. The Security Boundary

Here's a useful way to think like a backend engineer.

Your system has a boundary:

```text
              UNTRUSTED
                 |
                 v
        ┌──────────────────┐
        │ Incoming Request │
        └────────┬─────────┘
                 |
                 v
          SECURITY BOUNDARY
                 |
                 v
        ┌──────────────────┐
        │ Trusted Identity │
        └────────┬─────────┘
                 |
                 v
          Application Logic
```

The client controls the HTTP request.

Therefore:

> **You cannot blindly trust identity information supplied by the client.**

The server needs a mechanism to establish identity.

---

# 21. Why `X-User-Id` Is Fundamentally Weak

Your README currently documents:

```http
X-User-Id: <id>
```

for ownership operations. ([GitHub][1])

Imagine User 101 owns:

```text
Answer 500
```

A malicious client can simply send:

```http
X-User-Id: 101
```

The server sees:

```text
User ID = 101
```

But where did that identity come from?

The client.

The client is untrusted.

So we're effectively saying:

```text
Client:
    "Trust me, I'm User 101."

Server:
    "Okay."
```

That's not authentication.

---

# 22. What We Actually Want

We want:

```text
Client
   |
   | presents credentials/proof
   v
Server
   |
   | verifies
   v
Authenticated Identity
```

Then:

```text
Authenticated Identity
        |
        v
Authorization decision
```

The important difference is:

```text
BAD:

Client says:
"I am User 101."

GOOD:

Server verifies:
"This request is associated with User 101."
```

JWT will eventually give us one mechanism for carrying that authenticated identity between requests.

But don't jump ahead yet.

---

# 23. Why Authentication Happens Before Authorization

You can't meaningfully ask:

> "Is this person allowed to perform this operation?"

until you know:

> "Who is this person?"

Therefore:

```text
Authentication
       ↓
Identity
       ↓
Authorization
       ↓
Permission decision
```

For example:

```text
Who?
 ↓
User 101

Can User 101 update Question 500?
 ↓
Question owner = User 101
 ↓
YES
```

Without the identity:

```text
Can ??? update Question 500?
```

The question cannot be answered.

---

# 24. But Authorization Can Also Happen Without a User

There is one subtle point.

Consider:

```http
GET /questions
```

If the endpoint is public, we can make the authorization decision:

```text
Everyone is allowed.
```

No identity is necessary.

So authorization doesn't always require authentication.

Conceptually:

```text
Public resource
    ↓
Authorization rule:
"Everyone may access."
```

But for:

```text
PUT /questions/500
```

we need:

```text
Who?
```

before we can determine:

```text
Are they allowed?
```

This distinction becomes important when we configure Spring Security.

# 25. The Four States You Should Know

For any protected request, think in terms of these states:

```text
                  REQUEST
                     |
          ┌──────────┴──────────┐
          |                     |
    No authentication      Authentication
          |                     |
         401             ┌───────┴───────┐
                         |               |
                   Authorized       Not authorized
                         |               |
                        200             403
```

This is an excellent debugging mental model.

When you receive:

```http
401
```

think:

> **Authentication problem.**

When you receive:

```http
403
```

think:

> **Authorization problem.**

There are edge cases and configuration nuances, but this is the correct starting mental model.

# 26. The Difference Between Identity and Ownership

Another subtle but extremely important concept.

Suppose:

```text
Authenticated User = 101
```

This doesn't automatically mean:

```text
User 101 owns everything.
```

Authentication gives us:

```text
identity = 101
```

The database determines:

```text
Question 500 owner = 102
```

Then authorization compares them.

So:

```text
Authentication
      ↓
Current User = 101

Database/domain
      ↓
Resource Owner = 102

Authorization
      ↓
101 != 102
      ↓
DENY
```

This is why ownership authorization is usually a **business-level decision**.

---

# 27. Where Should Ownership Logic Live?

This is an important architectural question.

Suppose:

```text
QuestionService.updateQuestion(...)
```

needs to ensure:

```text
Current user owns question
```

Should we put this inside the controller?

Possible:

```text
QuestionController
       |
       +-- check owner
       |
       v
QuestionService
```

But this can become problematic because the same business operation might eventually be called from:

* REST API
* scheduled job
* admin workflow
* another service
* messaging consumer

The business rule belongs closer to the business operation.

A common design is:

```text
Controller
    |
    v
Service
    |
    +-- ownership/business authorization
    |
    v
Repository
```

We will revisit this deeply in **Stage 9**.

---

# 28. URL Authorization vs Business Authorization

This is an important distinction.

## URL-level authorization

Example:

```text
POST /questions
```

Rule:

```text
User must be authenticated.
```

This is relatively simple.

Conceptually:

```text
Request
   ↓
Is authenticated?
   ↓
YES → allow request to controller
```

---

## Business-level authorization

Example:

```text
PUT /questions/500
```

Rule:

```text
Authenticated user must own Question 500.
```

Now we need:

```text
Authenticated User ID
       +
Question 500
       ↓
Database/domain information
       ↓
Ownership comparison
```

This cannot always be decided merely from the URL.

---

# 29. Why This Distinction Matters for Spring Security

Spring Security is excellent at handling broad security rules such as:

```text
Public endpoint
Authenticated users
Admin-only endpoint
Role-based access
Authority-based access
```

But your application still owns domain-specific rules such as:

```text
Can this user modify this specific Question?
```

Spring Security doesn't magically understand:

```text
Question.owner
```

That's your domain model.

So the architecture becomes:

```text
Spring Security
      |
      | broad security
      v
"Is the requester authenticated?"
      |
      v
Application
      |
      | business authorization
      v
"Does this requester own Question 500?"
```

This separation is extremely important.

# 32. Authentication Is About Establishing Trust

A useful conceptual definition:

> **Authentication is the process by which the system establishes an identity for the requester.**

Not:

> "The user typed a username."

Not:

> "The client sent a user ID."

Not:

> "There is a `User` object."

The server needs a trustworthy authentication mechanism.

---

# 33. Authorization Is About Making a Decision

A useful conceptual definition:

> **Authorization is the process of deciding whether an authenticated identity is allowed to perform a particular action on a particular resource.**

Notice the important inputs:

```text
WHO
 ↓
Authenticated identity

WHAT
 ↓
Requested operation

WHICH
 ↓
Resource

RULE
 ↓
Application security/business policy
```

Then:

```text
ALLOW
or
DENY
```

---

# 34. A More Complete Authorization Formula

For a resource operation, think:

```text
Authorization Decision =

    Identity
    +
    Action
    +
    Resource
    +
    Policy
```

Example:

```text
Identity = User 101

Action = UPDATE

Resource = Question 500

Policy = Only owner can update

Question Owner = User 101
```

Therefore:

```text
ALLOW
```

Another request:

```text
Identity = User 102
Action = UPDATE
Resource = Question 500
Policy = Only owner can update
Question Owner = User 101
```

Therefore:

```text
DENY
```

This formula will become extremely useful when we reach `@PreAuthorize`, authorities, and ownership checks.

---

# 35. What Spring Security Does Not Know Automatically

This is worth emphasizing.

Spring Security can establish:

```text
Current authenticated user
```

But it doesn't automatically know:

```text
Question 500 belongs to User 101
```

That information lives in QueryNest's domain/database.

Therefore:

```text
Security identity
        +
Domain data
        =
Ownership decision
```

This is why learning Spring Security without understanding application architecture often causes confusion.

# Understanding Authentication and Authorization in QueryNest

In this stage, I learned that security is not just about blocking APIs. The two most important concepts are:

```text
Authentication
      ↓
Who are you?

Authorization
      ↓
What are you allowed to do?
```

The mistake I initially made was thinking:

```text
Authentication = legitimate user

Authorization = restrictions
```

While this is partially correct, there is a deeper understanding.

---

## Authentication Establishes Identity

Suppose a request comes into QueryNest:

```http
PUT /api/v1/questions/500
```

Before the application decides whether the update should happen, it first needs to know:

```text
Who is making this request?
```

Authentication answers this question.

After successful authentication, the application knows something like:

```text
Current User
      ↓
User ID = 101
Username = abhilash
Role = USER
```

The important thing I learned is that authentication is not just:

```text
true
or
false
```

Authentication establishes an identity for the current request.

---

## Why Identity Matters

Suppose:

```text
Question 500
      ↓
Owner = User 101
```

Now if someone tries to update Question 500, the application must know:

```text
Who is sending this request?
```

Without identity, ownership checks cannot happen.

---

## Why X-User-Id Is Not Enough

Earlier, QueryNest used:

```http
X-User-Id: 101
```

At first this looks useful.

But anyone can send:

```http
X-User-Id: 101
```

The problem is:

```text
The identity came from the client.
```

The server has not verified that claim.

This taught me an important rule:

```text
Client Claim
≠
Verified Identity
```

Just because a request contains:

```text
User ID = 101
```

does not mean the requester is actually User 101.

---

## Authorization Uses Identity

Once identity is established, the next question becomes:

```text
What is this user allowed to do?
```

This is authorization.

Suppose:

```text
Current User = 101
Question Owner = 101
```

Then:

```text
Authorization = SUCCESS
```

because the owner is performing the update.

But suppose:

```text
Current User = 102
Question Owner = 101
```

Then:

```text
Authorization = FAILURE
```

because the user does not own the resource.

---

## Authentication Can Succeed While Authorization Fails

This was one of the most important lessons.

Example:

```text
User 102 logs in successfully
```

Authentication:

```text
SUCCESS
```

Now User 102 tries:

```http
PUT /questions/500
```

but:

```text
Question Owner = 101
```

Therefore:

```text
Authorization = FAILURE
```

This means:

```text
Authentication SUCCESS
Authorization FAILURE
```

is completely possible.

---

## Understanding 401 and 403

### 401 Unauthorized

The system could not establish identity.

Example:

```text
Request arrives
No authenticated user
```

Result:

```http
401 Unauthorized
```

Think:

```text
Who are you?
I don't know.
```

---

### 403 Forbidden

The system already knows who you are.

But you are not allowed to perform the action.

Example:

```text
Current User = 102
Question Owner = 101
```

Result:

```http
403 Forbidden
```

Think:

```text
I know who you are.
You are not allowed.
```

---

## Role-Based Authorization vs Ownership Authorization

Another important thing I learned is that role alone is not always enough.

Suppose:

```text
User 101 = ROLE_USER
User 102 = ROLE_USER
```

and:

```text
Question 500 belongs to User 101
```

Both users have:

```text
ROLE_USER
```

So role alone cannot determine whether the update should happen.

The application must also check:

```text
Who owns the resource?
```

This is called ownership-based authorization.

---

## The Authorization Formula

For any protected operation, I can think about authorization using four things:

```text
Identity
+
Action
+
Resource
+
Policy
```

Example:

```text
Identity = User 101

Action = UPDATE

Resource = Question 500

Policy = Only owner can update
```

If:

```text
Question Owner = User 101
```

Result:

```text
ALLOW
```

Otherwise:

```text
DENY
```

---

## My Stage 1 Mental Model

Now I think about security like this:

```text
Request
   |
   v
Authentication
   |
   | Who are you?
   v
Current User
   |
   v
Authorization
   |
   | What are you allowed to do?
   v
ALLOW / DENY
```

The one sentence I want to remember is:

> Authentication establishes who the requester is; authorization decides whether that authenticated identity is allowed to perform the requested operation.
