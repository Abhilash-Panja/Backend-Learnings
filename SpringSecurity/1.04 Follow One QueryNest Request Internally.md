# Stage 4 — Follow One QueryNest Request Internally

> This is a merged edition combining both drafts of Stage 4, reorganized so the request flows in one continuous, linear story — Postman → Database → Response — with side-tables for the "why" behind each hop, and a debugging cheat sheet at the end.

Stage 3 gave you the **map**:

```text
Client
  ↓
Security Filter Chain
  ↓
Authentication
  ↓
SecurityContext
  ↓
Authorization
  ↓
Controller
  ↓
Service
  ↓
Repository
  ↓
Database
```

Stage 4 is about **walking that map with one real request**, in slow motion, until every arrow makes sense.

By the end, you should be able to explain — from memory, without diagrams — exactly what happens to an HTTP request *before* it ever reaches your controller.

---

## 🧭 The Request We're Following

```http
POST /api/v1/questions
Authorization: Bearer <JWT>
Content-Type: application/json

{
  "title": "How does Spring Security work?",
  "content": "I want to understand the request flow."
}
```

Assume the user already logged in earlier and received a JWT. Now they want to create a question.

**One rule to hold onto for this entire stage:**

> The client sends a **token** (proof), never an **identity claim** (like `"userId": 123`) that the server is expected to just believe. The server *derives* identity from the token — it never *trusts* an identity handed to it directly.

We'll see exactly why that matters in a few sections.

# Part 1 — From Postman to the Filter Chain

## 1.1 What Postman Actually Sends

Postman doesn't invoke `createQuestion()`. It sends raw bytes over HTTP:

```http
POST /api/v1/questions HTTP/1.1
Host: localhost:8080
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...

{
    "title": "What is dependency injection?",
    "description": "Explain DI in Spring Boot."
}
```

## 1.2 The Servlet Container Receives It First

Your Spring Boot app runs inside an **embedded servlet container** — commonly Tomcat.

```text
Postman
   ↓
HTTP
   ↓
Tomcat (Servlet Container)
```

Tomcat has **no idea** this is "a QueryNest question-creation operation." It only knows: *"I received an HTTP request for this path and method."*

## 1.3 Why Doesn't Tomcat Just Call the Controller Directly?

Because there are intermediary layers designed specifically to intercept the request first:

```text
Servlet Container
      ↓
Security Filters
      ↓
Spring MVC
      ↓
Controller
```

This is Spring Security's opportunity to inspect the request *before* your business code runs.

## 1.4 The Bridge: `DelegatingFilterProxy`

Here's a detail worth knowing (don't memorize the name — understand the *problem* it solves):

The servlet container understands **servlet filters** — a generic Java EE concept. But Spring Security's actual filter logic is a **Spring-managed bean**, living inside Spring's application context, not the servlet container's world.

Something has to bridge those two worlds:

```text
Servlet Container
       ↓
DelegatingFilterProxy   ← the bridge
       ↓
Spring Security
       ↓
SecurityFilterChain
```

`DelegatingFilterProxy` is a thin servlet filter whose only job is to hand control over to Spring's managed security infrastructure.

## 1.5 The Filter Chain Concept, Stripped Down

Forget Spring Security for a second. A generic filter just decides:

```text
Request
   ↓
Filter
   ↓
Should this continue?
   ├── NO  → reject
   └── YES → pass to next filter / controller
```

Spring Security builds a *sophisticated chain* of these:

```text
HTTP Request
      ↓
┌─────────────────────────────┐
│ Security Filter Chain       │
│  Filter A → e.g. JWT extract│
│  Filter B → e.g. auth check │
│  Filter C → e.g. exceptions │
│  Filter D → ...             │
└──────────────┬──────────────┘
               ↓
          Spring MVC
```

### Why not one giant filter?

| If everything lived in one filter... | Instead, we split responsibilities: |
|---|---|
| Handling auth + authorization + sessions + CSRF + exceptions + JWT + logout all in one place | Each filter owns exactly one job — the "chain of responsibility" pattern |
| Any change risks breaking unrelated behavior | Filters can be added, removed, or reordered independently |
| Nearly impossible to test in isolation | Each filter is small and testable on its own |

> ⚠️ **Don't memorize exact filter ordering.** Spring Security's internal filter list can change between versions. What's stable is the *architectural idea*: a chain, each link with one job, running before the controller.

# Part 2 — Authentication: Turning a Token Into an Identity

## 2.1 Finding the Token

The request carries:

```http
Authorization: Bearer eyJhbGciOi...
```

```text
Request
  ↓
Authorization header
  ↓
"Bearer eyJhbGciOi..."
  ↓
Extract token
```

`Bearer` is the **authentication scheme** — it tells the server *how* to interpret what follows:

```text
Authorization
     ├── Scheme      → Bearer
     └── Credentials → the JWT itself
```

The JWT-processing filter doesn't need to know anything about `QuestionController`. Its only question is: *"Does this request carry a token I know how to process?"*

## 2.2 Having a Token ≠ Being Authenticated

This is one of the most important ideas in the whole stage:

> **Possessing a JWT does not automatically mean the request is authenticated.** The server must *validate* it.

Validation typically involves:

- Signature verification
- Expiration check (`exp` claim)
- Issuer / audience validation
- Required claims present and well-formed

### Why signature verification specifically matters

Imagine an attacker crafts a fake token claiming:

```text
user = admin
```

If the server merely **decoded** the token (read its contents) without **verifying** its signature, the attacker could edit any claim they like — including elevating themselves to admin. That's why:

```text
Decode ≠ Validate
```

A correctly implemented JWT signature check proves the token wasn't tampered with after the server issued it.

## 2.3 Three Ways Validation Can Fail

| Failure | What happens | Result |
|---|---|---|
| **No token present** | Endpoint requires auth, nothing to check | `401` |
| **Malformed / invalid signature** | Token exists but fails cryptographic check | `401` |
| **Expired token** (`exp` has passed) | Signature might be fine, but token is stale | `401` |

In every one of these cases:

```text
Request
   ↓
JWT extraction
   ↓
Validation
   ↓
FAIL
   ↓
Authentication failure handling
   ↓
401
   ↓
QuestionController ❌ never executes
```

This is one of the biggest architectural payoffs of doing security *before* the controller: bad requests never get anywhere near your business logic or your database.

## 2.4 Validation Succeeds → Building `Authentication`

Suppose the token is valid and encodes:

```text
Identity = Abhilash (User 101)
```

Spring Security now builds its internal representation:

```text
Authentication
├── Principal    = Abhilash
├── Authorities  = [ROLE_USER]
└── authenticated = true
```

> The exact code that builds this depends on your JWT filter's implementation — but conceptually, this is a *translation step*: raw token claims → Spring Security's standard `Authentication` object.

## 2.5 A Subtlety: JWT Doesn't Automatically Query Your Database

A common beginner assumption:

```text
❌ "JWT arrives → Spring automatically re-fetches the user from the DB."
```

Not automatic. **You** decide, as part of your authentication design, whether to:

- Trust the token's claims directly (fast, but stale if the user's roles/status changed since token issuance), or
- Re-load the user from the database on every request (fresher, but adds a DB hit per request), or
- Some hybrid (e.g., trust claims but reject if the user was deleted/disabled, checked via a lighter mechanism).

### What if the token refers to a deleted or disabled user?

```text
JWT → userId = 123
User 123 has since been deleted
```

Should the server blindly proceed as if User 123 still exists? **No** — your authentication design should decide how "current user validity" gets checked. This is a real design decision you'll make in Stage 5+, not something Spring hands you for free.

> **Principle:** Authentication isn't just "decode the token." It's "establish a *trustworthy* current identity according to your application's security model."

# Part 3 — SecurityContext: Where the Identity Lives

## 3.1 The Problem This Solves

We now have an authenticated identity — but the controller, three layers away, doesn't automatically have access to it. We need a place to "park" that identity for the life of this one request.

```text
SecurityContext
       |
       └── Authentication
               ├── User 101 (Abhilash)
               └── ROLE_USER
```

## 3.2 `SecurityContextHolder`

This is the **global access point** for reading that context from anywhere in your code:

```text
SecurityContextHolder
        ↓
SecurityContext
        ↓
Authentication
        ↓
Principal (Abhilash)
```

Any layer — controller, service, even a utility method — can ask "who is currently authenticated?" without needing the raw HTTP request passed down through every method signature.

## 3.3 Why This Beats the Alternative

Imagine instead your controller looked like this:

```java
@PostMapping("/questions")
public Question createQuestion(
        @RequestHeader("Authorization") String token) {
    // parse JWT
    // validate JWT
    // find user
    // check permissions
    // create question
}
```

Now **every** protected endpoint re-implements security. Compare:

| Without SecurityContext | With SecurityContext |
|---|---|
| Every controller parses/validates tokens itself | Security layer does it once, upstream |
| Easy to forget a check on one endpoint | Centralized — hard to skip accidentally |
| Controller code mixes HTTP parsing + security + business logic | Controller only handles the business operation |

## 3.4 The Principle This Sets Up (Critical for Later Stages)

```json
{ "userId": 999, "title": "My question" }
```

Should the server treat `userId: 999` as "the current user"? **Absolutely not.** The client controls the request body — it's untrusted input.

```text
✅ Trusted identity source:
JWT → Authentication → SecurityContext → "current user"

❌ Untrusted identity source:
Request body field like "userId"
```

> **The client presents credentials/proof. The server establishes identity. Application logic then uses the server-established identity — never a client-supplied identity field.**

This single principle is what makes ownership checks (Stage 9) actually secure instead of trivially spoofable.

# Part 4 — Authorization: Now That We Know *Who*, Decide *What*

## 4.1 Authentication Answered "Who." Authorization Answers "What Can They Do."

```text
Authentication
      ↓
Who?  → Abhilash

Authorization
      ↓
What can they do? → Create a question?
```

## 4.2 URL-Level Authorization (Coarse-Grained)

QueryNest might define broad rules like:

| Endpoint | Rule |
|---|---|
| `POST /auth/register`, `POST /auth/login` | Public |
| `GET /questions` | Public |
| `POST /questions`, `POST /answers` | Authenticated (any `ROLE_USER`) |
| `DELETE /users/{id}` | `ROLE_ADMIN` only |

These are decisions the security layer can make *without* touching your domain data — just role/authentication status vs. the URL pattern.

```text
Request
   ↓
Authorization rules
   ↓
Allowed?
```

## 4.3 Case: No Authentication at All

```http
POST /api/v1/questions
```
*(no token)*

```text
                POST /questions
                       ↓
               Security Filter
                       ↓
              Authentication?
                 /          \
               NO            YES
               ↓              ↓
              401         Authorization
                              ↓
                           Controller
```

`QuestionController` never runs. Nothing touches the service, repository, or database.

## 4.4 Case: Authenticated, but URL-Level Authorization Fails

```text
User = Abhilash, ROLE_USER
Endpoint requires: ROLE_ADMIN
```

```text
JWT
 ↓ valid
Authentication
 ↓
Abhilash / ROLE_USER
 ↓
Authorization
 ↓
Requires ROLE_ADMIN
 ↓
FAIL
 ↓
403
```

Notice: **authentication succeeded**, but **authorization failed**. This is precisely the 401-vs-403 distinction from Stage 1 and 3, now seen at the *runtime* level.

| | Authentication | Authorization | Result |
|---|---|---|---|
| No token / invalid token | ❌ | — | `401` |
| Valid token, insufficient role | ✅ | ❌ | `403` |
| Valid token, sufficient role | ✅ | ✅ | Controller runs |

# Part 5 — Past the Gate: Controller → Service → Repository → Database

## 5.1 Controller's (Now Narrow) Job

By the time `QuestionController` executes, security has already:

- Confirmed the request is authenticated
- Established *who* the user is (available via `SecurityContext`)
- Confirmed they're authorized at the URL level

So the controller **does not** need to re-check any of that. It focuses purely on:

```text
HTTP request/DTO
     ↓
QuestionController.createQuestion(...)
     ↓
delegate to QuestionService
```

## 5.2 Where Does the User ID Actually Come From Here?

This is the payoff of everything in Part 3. The service needs to know "who is creating this question?" It does **not** get that from the request body:

```text
❌ Bad:  Question.owner = request.getUserId()   (client-controlled, spoofable)
✅ Good: Question.owner = SecurityContextHolder → Authentication → Principal → User 101
```

```text
JWT
 ↓
Authentication
 ↓
SecurityContext
 ↓
Authenticated user (101)
 ↓
Question.owner = 101
```

## 5.3 Service → Repository → Database

```text
QuestionService
      ↓
Create Question entity (owner = authenticated user)
      ↓
QuestionRepository
      ↓
Hibernate/JPA
      ↓
Database
      ↓
INSERT INTO question ...
```

Spring Security's job ends once authorization passes. It is **not** responsible for saving your data — that's squarely the domain/persistence layer's job.

## 5.4 The Response Flows Back Up

```text
Database
   ↓
Repository
   ↓
Service
   ↓
Controller
   ↓
HTTP Response (e.g. 201 Created)
   ↓
Client
```

# Part 7 — Three Full Scenarios, Side by Side

| | **A. Unauthenticated** | **B. Authenticated + Authorized** | **C. Authenticated, Unauthorized** |
|---|---|---|---|
| Request | `POST /questions` (no token) | `POST /questions` + valid JWT | `DELETE /users/50` + valid JWT (ROLE_USER) |
| Authentication | ❌ Fails — no valid identity | ✅ Succeeds — User 101 | ✅ Succeeds — User 101 |
| Authorization | *(never reached)* | ✅ Authenticated users may create questions | ❌ Requires ROLE_ADMIN |
| `QuestionController` runs? | ❌ No | ✅ Yes | ❌ No |
| `QuestionService` runs? | ❌ No | ✅ Yes | ❌ No |
| Database touched? | ❌ No | ✅ Yes | ❌ No |
| HTTP status | `401` | `201 Created` (or `200`) | `403` |

This table is worth memorizing in shape, not in specifics — it's the pattern you'll use to debug *any* future security issue.

# Part 8 — The Layer Beyond URL Rules: Ownership / Business Authorization

## 8.1 The Scenario That Breaks Pure Role-Based Rules

QueryNest's actual policy is more specific than "any `ROLE_USER` can update questions":

> Only the question's **owner** can update it.

Consider:

```text
Question 101
Owner = User A (id 50)
```

User B (id 101, `ROLE_USER`) sends:

```http
PUT /api/v1/questions/101
Authorization: Bearer <User-B-JWT>
```

At the **URL-level** authorization stage:

```text
User B is authenticated: ✅
User B has ROLE_USER:    ✅
Policy: "ROLE_USER may call PUT /questions/{id}": ✅ ALLOW
```

So the request **passes** the security filter chain and reaches the controller! But that's not the whole story — we still haven't checked *ownership*.

## 8.2 Where the Second Check Happens

```text
JWT
 ↓
Authenticated User = B (101)
 ↓
URL-level authorization: ALLOW (has ROLE_USER)
 ↓
QuestionController
 ↓
QuestionService
 ↓
Load Question 101 from DB
 ↓
Question.owner = A (50)
 ↓
Compare: authenticated user (101) vs. owner (50)
 ↓
101 != 50
 ↓
REJECT (typically 403, raised from inside the service/business layer)
```

## 8.3 Why This *Isn't* a Contradiction of "Security Happens Before the Controller"

It looks like the controller "ran" even though the request should ultimately be denied. But look closely — **two different kinds of authorization** are at play:

| | Checked by | Depends on | Example |
|---|---|---|---|
| **URL-level authorization** | Spring Security filter chain | Role/authentication status only | "Is this user *a* USER at all?" |
| **Business/ownership authorization** | Your service layer | Domain data (who owns what) | "Is this user *the owner of Question 101*?" |

Spring Security can't answer the second question on its own — it has no idea `Question.owner` exists. That's **your domain model**, living in **your database**. So:

```text
Spring Security
    ↓
broad, identity-based rules

Application / Service layer
    ↓
domain-specific, data-dependent rules
```

## 8.4 Why Ownership Checks Usually Belong in the Service Layer

If you scatter `if (question.owner != currentUser) reject;` across `QuestionController`, `AnswerController`, `AdminController`, etc., you get the same duplication problem filters were invented to solve in the first place. Putting it in `QuestionService` means:

- The rule lives in one place, next to the operation it protects
- Any caller of that service method — REST API, admin tool, scheduled job — gets the same protection automatically
- Controllers stay thin: HTTP in, HTTP out

We'll build this properly in **Stage 9**.

# Part 9 — Runtime Responsibilities, Layer by Layer

| Layer | Responsibility | Explicitly NOT responsible for |
|---|---|---|
| **Servlet Container** | Receive raw HTTP request | Understanding your app's routes/security |
| **Spring Security** | Authentication, SecurityContext, coarse-grained authorization | Domain rules like "who owns this question" |
| **Controller** | HTTP ↔ DTO translation, delegate to service | Re-validating tokens, re-checking roles |
| **Service** | Business logic, ownership/business authorization | Persistence mechanics, HTTP concerns |
| **Repository** | Persistence (via JPA/Hibernate) | Business rules |
| **Database** | Store the data | Everything above this line |

This separation matters because it stops any single layer from silently becoming "responsible for everything," which is exactly how security holes get introduced.

# Part 10 — Failure Modes Explained

## 10.1 Malformed / Tampered Token

```http
Authorization: Bearer abc123
```
*(not actually a valid JWT structure or signature)*

```text
Request → JWT extraction → Validation → INVALID → 401
```

## 10.2 Expired Token

```text
exp = 10:00 AM
Request arrives = 10:30 AM
```

```text
JWT → signature OK → expiration check → FAIL → 401
```

Expiration isn't a formality — it's an active security control that limits how long a stolen token remains useful.

## 10.3 Token References a Deleted/Disabled User

```text
JWT → userId = 123 (but User 123 no longer exists / is disabled)
```

Whether this results in `401` depends entirely on **your** authentication design — this is a deliberate decision you'll make, not something automatic. The lesson: *"decoding a valid-looking token" and "having a trustworthy identity"* are not the same guarantee.

# Part 11 — A More Honest Mental Model

It's tempting to oversimplify Spring Security as:

> "Security happens before the controller."

That's a great *starting* mental model, but it's incomplete — security can also apply **inside** the controller/service layer (e.g., `@PreAuthorize`, method-level checks, and the ownership checks from Part 8). The more accurate version:

> **Spring Security establishes and enforces security boundaries around your application's execution — the filter chain is the biggest, earliest boundary, but not the only one.**

# 🧩 Debugging Cheat Sheet

When something goes wrong, don't immediately start editing `SecurityFilterChain` code. Walk this checklist instead:

### Getting a `401`?
```text
Did the request reach the security filter chain?
   ↓
Was a token/credential present at all?
   ↓
Was it valid (signature, format, expiration)?
   ↓
Was an Authentication object successfully created?
   ↓
Was SecurityContext populated?
```

### Getting a `403`?
```text
Authentication almost certainly succeeded — so:
   ↓
Who is the authenticated principal? (log it)
   ↓
What authorities/roles does it have?
   ↓
Which specific rule rejected it — URL-level or business/ownership?
```

### Controller "sees" the wrong user / no user?
```text
Was Authentication actually created for this request?
   ↓
Was SecurityContext populated before the controller ran?
   ↓
Are you reading identity from SecurityContext — or accidentally trusting a client-supplied field?
```

This systematic approach is far more durable than memorizing `.requestMatchers(...).hasRole(...)` syntax, because it survives framework version changes.

# Stage 4 Summary — The One Paragraph to Internalize

> A request first hits the servlet container, which hands it to Spring Security's filter chain via `DelegatingFilterProxy`. The chain extracts and validates any credential (like a JWT); if that fails, the request is rejected with `401` before the controller ever runs. If it succeeds, Spring Security builds an `Authentication` object and stores it in the `SecurityContext`, making the identity available application-wide without trusting anything from the request body. Authorization then checks coarse-grained rules (role vs. endpoint); failure here means `403`. Only after both checks pass does the controller execute, delegating to the service layer — which may still apply *business-level* authorization (like ownership) using domain data Spring Security has no visibility into. Only then does data reach the repository and the database.

If you can say that from memory, you've internalized Stage 4.
