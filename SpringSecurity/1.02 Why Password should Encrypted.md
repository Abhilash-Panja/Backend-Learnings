# Stage 2 — Passwords, Hashing, Salt, BCrypt & PasswordEncoder

The question for this stage is:

> **Once we know that a user is supposed to prove their identity using a password, how do we safely store and verify that password?**

This is the foundation we need before we introduce `UserDetailsService`, `AuthenticationProvider`, `AuthenticationManager`, JWT, etc.

Your learning path explicitly puts password storage, hashing, salt, BCrypt, `PasswordEncoder`, and login verification before the Spring Security architecture.

---

## 1. Start With QueryNest

Let's forget Spring Security again.

Suppose a new QueryNest user registers:

```text
username = abhilash
password = MySecretPassword123
```

Your backend receives:

```http
POST /api/v1/users
```

with something like:

```json
{
    "username": "abhilash",
    "password": "MySecretPassword123"
}
```

Now the backend needs to persist the user.

The naive thought is:

```text
Request
   ↓
UserService
   ↓
UserRepository
   ↓
MySQL
```

and eventually:

```text
username = abhilash
password = MySecretPassword123
```

stored in the database.

### Stop here.

Would that be okay?

**Absolutely not.**

This is the first security problem we're going to solve.

---

## 2. Why Is Plain-Text Password Storage Dangerous?

Imagine your database contains:

```text
id    username    password
-----------------------------------
101   abhilash    MySecret123
102   rahul       Rahul@123
103   john        JohnPassword
```

At first glance, the application can easily verify a login:

```text
User enters:

username = abhilash
password = MySecret123

             ↓

Database:

password = MySecret123

             ↓

Compare

             ↓

MATCH
```

It works.

But engineering isn't about asking:

> "Does it work?"

We ask:

> **"What happens when something goes wrong?"**

### Imagine the database gets leaked

Suppose an attacker obtains a copy of the database.

If passwords are stored directly:

```text
Attacker
   ↓
Database dump
   ↓
username + actual password
```

The attacker immediately has the user's password.

And this is much worse than just losing access to QueryNest.

### Password reuse

Many users reuse passwords across websites.

For example:

```text
QueryNest:
MySecret123

Gmail:
MySecret123

GitHub:
MySecret123

Bank:
MySecret123
```

So a QueryNest database breach could potentially compromise accounts elsewhere.

Therefore:

> **Your database should never contain the user's original password.**

---

## 3. "What If We Encrypt the Password?"

This is where an important distinction begins.

You might think:

> "Okay, let's encrypt the password."

For example:

```text
Plain password
      ↓
Encryption
      ↓
Encrypted password
      ↓
Database
```

That sounds secure.

But password storage generally doesn't need encryption.

Why?

Because encryption is **reversible**.

---

## 4. Encryption

Imagine:

```text
Encryption:

"MySecret123"
      ↓
"X7f82K..."
```

And later:

```text
"X7f82K..."
      ↓
Decryption
      ↓
"MySecret123"
```

There is a key that allows us to recover the original value.

Conceptually:

```text
Plaintext
   ↓
Encryption + Key
   ↓
Ciphertext

Ciphertext
   ↓
Decryption + Key
   ↓
Plaintext
```

This is useful when we **need to recover the original data**.

Examples:

* encrypted files
* encrypted communication
* encrypted sensitive data that the application must later retrieve

But think about passwords.

Does QueryNest actually need to know:

```text
What was the user's original password?
```

No.

It only needs to answer:

> **"Does the password supplied during login match the password the user originally chose?"**

That's a different problem.

---

## 5. We Don't Need the Original Password

This is the key insight.

During registration:

```text
User enters:

MySecretPassword123
```

We don't need to store:

```text
MySecretPassword123
```

Instead, we can transform it into another representation.

Conceptually:

```text
MySecretPassword123
        ↓
     Hashing
        ↓
Some derived value
        ↓
      Database
```

Later, during login:

```text
User enters password
        ↓
Apply same password-verification process
        ↓
Compare with stored representation
        ↓
MATCH / NO MATCH
```

We never need to recover the original password.

That is why password storage uses **one-way password hashing**, rather than reversible encryption.

---

## 6. Hashing vs Encryption

Let's make this distinction extremely clear.

### Encryption

```text
Plaintext
   ↓
Encryption
   ↓
Ciphertext
   ↓
Decryption
   ↓
Plaintext
```

It is designed to be reversible by someone who possesses the appropriate key.

### Hashing

Conceptually:

```text
Input
   ↓
Hash function
   ↓
Derived value
```

You don't use the resulting hash to recover the original password.

For example:

```text
"MySecret123"
      ↓
   Hashing
      ↓
"8f4a..."
```

The important property is:

```text
password
   ↓
hash
```

but not:

```text
hash
   ↓
original password
```

### Quick-reference comparison

| Property                            | Encryption | Password Hashing |
| ------------------------------------ | ---------- | ----------------- |
| Designed to be reversible            | Yes        | No                 |
| Requires a decryption key            | Yes        | No                 |
| Application needs the original value later | Usually    | No                 |
| Typical use for password storage     | No         | Yes                |
| Example                              | AES        | BCrypt             |

The exact algorithms aren't the important part to remember — the important architectural question is:

> **Do we need to recover the secret, or only verify it?**

For passwords: only verify. That's why hashing, not encryption, is the right tool.

---

## 7. But There Is a Problem With Normal Hashing

Now we're getting to an important security-engineering insight.

You might say:

> "Great. I'll just use SHA-256."

For example:

```text
password
   ↓
SHA-256
   ↓
hash
   ↓
database
```

Better than plain text.

But **not ideal for password storage**.

Why?

Because general-purpose cryptographic hash functions are designed to be extremely fast.

That's normally a good property.

For example:

```text
SHA-256
    ↓
very fast
```

But for passwords, we actually want password processing to be deliberately expensive.

Why?

Because attackers can perform enormous numbers of guesses.

---

## 8. The Attacker's Problem

Suppose the attacker has stolen:

```text
username = abhilash
password_hash = ABC123...
```

They don't necessarily need to reverse the hash.

They can try guesses.

For example:

```text
password1
123456
qwerty
password
MySecret123
...
```

For each guess:

```text
Guess
 ↓
Hash
 ↓
Compare with stolen hash
```

If the hash matches:

```text
Correct password found
```

The attacker can automate this.

---

## 9. Why Fast Hashing Is Actually Bad for Passwords

Imagine an attacker has hardware capable of testing:

```text
1,000,000,000 guesses/second
```

A fast hash makes password guessing cheaper.

We therefore want a password hashing algorithm to make each guess relatively expensive.

Not:

```text
guess → instant
```

but something closer conceptually to:

```text
guess
 ↓
expensive computation
 ↓
result
```

This is one of the reasons password-specific hashing algorithms exist.

And this leads us to:

## BCrypt

---

## 10. BCrypt

BCrypt is a password hashing algorithm designed specifically for password storage.

Its design intentionally makes password hashing computationally expensive.

Conceptually:

```text
Password
    ↓
BCrypt
    ↓
Expensive computation
    ↓
Password hash
```

Then:

```text
Database
---------------------------------
username       password_hash
abhilash       $2a$10$...
```

Notice something important.

The database does **not** contain:

```text
MySecretPassword123
```

It contains a derived password representation.

---

## 11. "But If Hashing Is One-Way, How Do We Verify Login?"

Excellent question.

This is where many beginners misunderstand password hashing.

Suppose registration happens.

User enters:

```text
MySecretPassword123
```

BCrypt produces something like:

```text
$2a$10$N9qo8uLOickgx2ZMRZoMye...
```

We store that.

Later:

```text
Login password:
MySecretPassword123
```

How can the server know they're equal?

It doesn't decrypt the stored value.

Instead, the password verification mechanism takes:

```text
Raw password
+
Stored password hash
```

and asks:

```text
Does this raw password correspond
to this stored password hash?
```

Conceptually:

```text
             ┌───────────────────┐
raw password │ MySecretPassword  │
             └─────────┬─────────┘
                       │
                       ▼
              Password verifier
                       ▲
                       │
             ┌─────────┴─────────┐
stored hash  │  $2a$10$N9qo...   │
             └───────────────────┘

                       ↓

                 MATCH / NO MATCH
```

This is fundamentally different from:

```text
decrypt(storedHash)
```

There is no need to recover the original password.

---

## 12. Now We Reach SALT

Here's another problem.

Suppose two users choose the same password:

```text
Abhilash:
password = hello123

Rahul:
password = hello123
```

If we simply use a deterministic hash:

```text
hash("hello123")
```

both users get:

```text
same hash
```

For example:

```text
Abhilash → ABCXYZ
Rahul    → ABCXYZ
```

That's undesirable.

Why?

Because attackers can identify users with the same password.

Even worse, attackers can precompute hashes for common passwords.

---

## 13. Enter Salt

A **salt** is additional random data incorporated into password hashing.

Conceptually:

```text
Password
   +
Random Salt
   ↓
Password Hashing
   ↓
Stored Hash
```

For example:

```text
User A:

password = hello123
salt     = X7K9...
       ↓
hash     = ABC123...
```

Another user:

```text
User B:

password = hello123
salt     = P2Q8...
       ↓
hash     = XYZ789...
```

Same password.

Different salt.

Different resulting hash.

---

## 14. Why Is Salt Important?

Without salt:

```text
hello123
   ↓
HASH
   ↓
ABC123

hello123
   ↓
HASH
   ↓
ABC123
```

With salt:

```text
hello123 + randomSaltA
       ↓
     HASH
       ↓
   ABC123

hello123 + randomSaltB
       ↓
     HASH
       ↓
   XYZ789
```

So an attacker cannot simply look at the database and conclude:

```text
These two users use the same password.
```

It also makes precomputed password-hash lookup attacks much less useful.

---

## 14.5 Is the Salt a Secret?

Quick clarification before we go further, because it trips people up:

**No — the salt does not need to be kept secret.**

The security of salted hashing doesn't come from *hiding* the salt. It comes from the salt being **unique per user**, which:

- prevents two identical passwords from producing identical hashes, and
- defeats precomputed lookup tables (rainbow tables), since an attacker would need a separate precomputed table *per salt*, which defeats the purpose of precomputing anything.

So it's completely fine — and normal — for the salt to be stored right alongside the hash, visible to anyone who has database access. Security comes from:

```text
unique random salt
   +
strong password hashing algorithm
```

not from secrecy of the salt itself.

---

## 15. "Where Do We Store the Salt?"

This is an excellent engineering question.

You might think:

```text
password_hash
salt
```

must be stored separately.

With modern password hashing algorithms such as BCrypt, the salt is incorporated into the encoded password representation.

So the stored value itself contains the information necessary for verification.

Conceptually:

```text
Stored BCrypt value
        |
        +---- algorithm information
        +---- cost/work factor
        +---- salt
        +---- derived password value
```

So when we later verify the password, the password-verification mechanism can obtain the necessary information from the stored BCrypt value.

You don't normally need a separate:

```java
String salt;
```

column for BCrypt.

---

## 16. Important Mental Model

Don't think:

```text
User
 ├── password
 └── salt
```

and then manually implement:

```java
generateSalt();
hashPassword();
storeSalt();
```

when using BCrypt through Spring Security.

Instead think:

```text
Raw Password
     ↓
Password Hashing Algorithm
     ↓
Encoded Password Representation
     ↓
Database
```

The algorithm manages the password-specific details.

---

## 17. Why BCrypt Is Better Than "Just SHA-256"

Let's compare conceptually.

### SHA-256

Designed as a general-purpose cryptographic hash.

```text
password
   ↓
SHA-256
   ↓
fast hash
```

### BCrypt

Designed for password storage.

```text
password
   ↓
BCrypt
   ↓
deliberately expensive computation
   ↓
password hash
```

The goal isn't to make BCrypt mathematically "more one-way" than SHA-256.

The important difference is:

> **Password hashing is designed around the economics of password guessing.**

That's the senior-engineer way of thinking about it.

---

## 18. What Is the "Cost" in BCrypt?

BCrypt has a configurable work factor, often called the **cost**.

Conceptually:

```text
Cost
 ↓
How much computational work should BCrypt perform?
```

Higher cost:

```text
more computation
↓
slower password verification
↓
harder for attackers to perform huge numbers of guesses
```

But there's a trade-off.

If you make it excessively expensive:

```text
Login request
    ↓
very expensive BCrypt operation
    ↓
slow application
```

So production systems choose a cost appropriate for their infrastructure and periodically reassess it.

### Why not just max out the cost, then?

Because legitimate users pay the same cost attackers do — just once per login instead of billions of times.

```text
Cost too low  → attacker can brute-force cheaply
Cost too high → every real login becomes slow, server load increases,
                 legitimate users suffer
```

If your server suddenly receives 1,000 login requests, an excessively expensive cost factor multiplies that load 1,000×. So the cost factor is deliberately tuned to be *expensive enough to hurt brute-force at scale* while staying *cheap enough for one legitimate login to feel instant*.

Again:

> Security is usually a trade-off, not a magic number.

Now imagine:

```http

```

with:

```json

    "username": "abhilash",
    "password": "MySecret123"

```

The backend should conceptually perform:

```text
username
   ↓
Find user
   ↓
Retrieve stored password hash
   ↓
Take supplied raw password
   ↓
Password verification
   ↓

```

If:

```text
MATCH
```

then:


If:


## 22. Where Does `PasswordEncoder` Come In?

Now we can introduce our **first Spring Security abstraction**.

Don't memorize:

```java
PasswordEncoder
```

Instead ask:

> **What problem do we need to solve?**

We need an abstraction for:

```text
Raw password
      ↓
Secure password encoding
```

and:

```text
Raw login password
      +
Stored encoded password
      ↓
Verification
```

Spring Security provides the abstraction:

```text
PasswordEncoder
```

Conceptually:

```text
                PasswordEncoder
                      |
          ┌───────────┴───────────┐
          ↓                       ↓
     Encode password          Verify password
          ↓                       ↓
     Registration                Login
```

---

## 23. Two Different Operations

This distinction is important.

### During registration

We need:

```text
raw password
      ↓
encode(...)
      ↓
stored password
```

Conceptually:

```java
String encodedPassword =
        passwordEncoder.encode(rawPassword);
```

The important concept is:

> Convert the user's raw password into the secure representation that we store.

### During login

We need:

```text
raw login password
        +
stored encoded password
        ↓
matches(...)
        ↓
true / false
```

Conceptually:

```java
passwordEncoder.matches(
    rawPassword,
    storedPassword
);
```

Notice that we don't do:

```java
encode(rawPassword).equals(storedPassword)
```

That is an important point.

---

## 24. Why Not Simply Encode Again and Compare?

Suppose:

```text
password = MySecret123
```

During registration:

```text
BCrypt(password)
    ↓
hash A
```

During login, BCrypt uses a new random salt if you simply encode again:

```text
BCrypt(password)
    ↓
hash B
```

You could get:

```text
hash A != hash B
```

even though the passwords are identical.

That's exactly why the verification API exists.

Conceptually:

```text
matches(rawPassword, storedHash)
```

knows how to use the information encoded in the stored password representation to perform the comparison correctly.

---

## 25. Very Important: `encode()` Does Not Mean Encryption

This is another terminology trap.

When Spring Security calls:

```java
passwordEncoder.encode(password)
```

you should **not** mentally translate it to:

```text
encrypt(password)
```

Think:

```text
encode()
   ↓
password hashing / password transformation
   ↓
one-way stored representation
```

The API uses the generic word `encode`, but for BCrypt we're dealing with password hashing, not reversible encryption.

## 28. What Happens If the Database Is Stolen?

This is the test we should always perform.

Suppose the database contains:

```text
abhilash
$2a$10$N9qo8uLOickgx2ZMRZoMye...
```

The attacker doesn't see:

```text
MySecretPassword123
```

They see the password hash representation.

The attacker can still attempt password guessing, which is why strong passwords, appropriate password hashing parameters, rate limiting, and other controls matter.

But a database leak no longer immediately reveals every user's original password.

That's the security improvement we're trying to achieve.

---

## 29. What If the User Has a Very Weak Password?

Suppose:

```text
password = 123456
```

BCrypt doesn't magically make:

```text
123456
```

a strong password.

It gives you a secure way to **store and verify** the password.

An attacker who guesses:

```text
123456
```

may still succeed.

Therefore:

```text
Strong password
       +
Strong password hashing
       +
Rate limiting
       +
Account protection
```

work together.

This distinction is important:

> **Password hashing protects stored credentials; it does not make weak passwords strong.**

## 33. One More Important Point: Don't Log Passwords

This sounds obvious, but it is a common real-world mistake.

Never do:

```java
log.info("User password: {}", password);
```

Don't put raw passwords into:

* application logs
* exception messages
* database audit records
* debugging output
* API responses

The password should have a very short lifetime inside your application:

```text
HTTP request
     ↓
raw password
     ↓
verification / encoding
     ↓
no longer needed
```

And the stored form should be the encoded representation.

## 39.5 What You Should Be Able to Say in an Interview

If someone asks:

> "Why don't you store passwords directly in the database?"

A weak answer sounds like:

> "Because Spring Security recommends BCrypt."

A strong answer sounds like:

> "Because the database might be compromised, and the application never actually needs to recover a user's original password — it only needs to verify whether a login attempt matches what the user originally chose. So passwords should be stored using a one-way hashing mechanism rather than plain text or reversible encryption. A password-specific algorithm like BCrypt also adds a per-user salt and a configurable, deliberately expensive cost factor, which makes large-scale password guessing significantly more costly for an attacker while staying fast enough for a single legitimate login."

Notice the second answer never leans on "because the framework says so" — it reconstructs the reasoning from the actual threat model. That's the difference this whole stage is trying to build in you.
